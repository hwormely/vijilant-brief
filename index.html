Screen 01
Sign In
— First access · All roles
Live Prototype
Role

Entry point for all users. Email + password authentication with SSO option. HIPAA-compliant biometric auth (Face ID / Touch ID) is enforced after first login — no passcode fallback option is ever presented.

Layout
  • Full gradient hero — teal→navy background on mobile. Glass card (backdrop-filter blur) on desktop.
  • Vijilant wordmark — DM Mono, logo mark with gradient accent. Top of the login surface.
  • Form fields — email (focused = teal border), password, forgot password link.
  • CTA — teal gradient button on dark background. SSO ghost button below divider.
UX Decisions
  • No passcode fallback is ever offered — HIPAA requires biometric-only on mobile handling PHI.
  • Staff invited via link land on Accept Invite (Screen 02), not this screen.
  • Gradient background creates immediate brand recognition before any interaction.

Screen 02
Accept Invite
— First-run setup · Runs once
Live Prototype
Role

First-run experience shown once when a staff member activates their account via an invite link. Configures name, password, and HIPAA acknowledgment. Not reachable from within the app after completion.

Layout
  • Full gradient hero — org name and role pre-filled from the invite token.
  • Name + password fields — set and confirm password.
  • HIPAA acknowledgment — teal checkbox required before CTA enables.
  • Gradient CTA — "Activate Account →" on dark background.
UX Decisions
  • Role and org are pre-populated from the invite — staff does not self-select their role.
  • HIPAA acknowledgment is required at account activation, not buried in settings.
  • Single decision per step reduces cognitive load at first launch.

Screen 04
Dashboard — My Day
— Daily anchor · Home screen · Case Manager
Live Prototype
Role

Opens on every app launch. The morning brief — designed to answer "what needs my attention today?" without requiring the CM to go hunting. Not a list of all cases; a prioritized summary of what matters now.

Layout
  • Gradient hero — personalized greeting, 2×2 stat cards on mobile.
  • KPI strip (desktop, 5 cards, single row) — Active Clients · Notes This Week · Follow-ups Done · Assessments · Aid Apps. Never stacked.
  • 3-column module row (desktop) — Overdue Follow-ups · Score Drop Alerts (≥100 pts/30d) · New Resources (last 14d).
  • Overdue follow-ups — each row: client name · days overdue · compact 36px gradient ring.
  • Score drop alerts — clients whose Recovery Score dropped ≥100 pts in 30 days. Delta in coral.
  • Recent Activity — full-width below. Chronological feed.
UX Decisions
  • Morning-brief model — system decides priority; CM reads and acts.
  • Score drop alerts surface deteriorating cases before they become escalations.
  • New Resources module drives organic adoption of newly added programs.
  • Period filter (Today / This Week / Month / Quarter) re-scopes all modules simultaneously.

Screen 06
Client List — My Cases
— Full caseload browser · CM sees "My Cases" · Supervisor sees "All Clients"
Live Prototype
Role

Full caseload in one scrollable list. Used when the CM needs a specific case not surfaced on the Dashboard, or when doing a status review across all active clients.

Layout
  • Gradient header — page title, search bar, filter tabs (All / T1 / T2 / T3 / Closed).
  • LLP highlight borders — left border per row: red = no longer seeking; coral = active outreach; gray = standard.
  • Row content — initials avatar · client name · case ID + last contact · triage tier badge · 36px gradient ring + ? icon.
  • Desktop — table view: Client / Case ID / Tier / Recovery Ring / Last Contact / Status.
Recovery Score Ring

Every client row displays a compact 36×36px Recovery Score Ring at the trailing edge. The gradient arc (Red→Coral→Teal→Navy) reflects the full 0–1000 scale; the filled portion shows the client's current score. Score color matches the band. A ? icon opens a domain-level explainer popover. Score is never manually entered.

UX Decisions
  • Triage tier badge is the first signal in the visual scan — tier before name.
  • Last-touch date surfaces recency without opening the case.
  • Default sort: Last Updated. Most recently touched cases first.
  • Closed cases remain searchable and auditable but are visually de-emphasized.

Screen 07
Client Detail
— Central hub for a single client · 7 tabs · Applications tab shown
Live Prototype — Applications Tab
Role

Everything about one client in one place. Notes, assessments, plans, and aid applications are all tabs within this screen — not separate screens reached from a menu.

Layout
  • Gradient hero strip — client avatar, name, case ID, tier badge, disaster event tag. 72px Recovery Score Ring in the right portion of the hero.
  • Tab bar (7 tabs, locked order) — Notes · Assessments · Recovery Plan · Follow-ups · Applications · Documents · Resources.
  • Applications tab — application list with status badges. Tapping Auto-Draft or In Progress opens form view.
  • Form view — auto-filled fields (green left border, #F0FAF5 bg, "Auto-filled" chip). Submission mode selector (Email / External Form / API). Gradient CTA: "Submit Application". Audit trail below form.
Recovery Score Ring (72px)

The client header displays the 72×72px Recovery Score Ring — the primary visual landmark for a client's recovery status. Same gradient arc as compact ring. Score delta vs. 30 days prior. A ? opens the domain-level explainer: Housing Stability · Financial Recovery · Emotional Wellbeing · Documentation · Support Network.

Screen 08
Assessment
— 12-section clinical form · Client Detail tab
Live Prototype
Role

Full Assessment is where CMs document the complete clinical picture across 12 structured sections. When the assessment is saved, the Auto-Triage Engine reads every section and assigns an official Tier designation automatically. CMs never touch the tier directly.

Layout
  • Domain tabs — Housing · Employment · Mental Health · Financial · Legal. Active = teal. Completed = checkmark overlay.
  • Progress bar — "Domain X of 5" + overall percentage. Always visible.
  • Completed domain summary — Q&A display in → [answer_label] format. Domain pill (None / Disrupted / Partial / Stable / Strong).
  • Active domain questions — text-only descriptive radio labels. NO numeric prefixes ever.
  • Gradient CTA — "Next Question →" on white background uses teal→coral→navy gradient.
Assessment Rules — LOCKED
  • Radio labels are text-only descriptive. Never "1 —", "2 —", or any numeric prefix.
  • The 1–5 internal scoring scale is server-side only. Never rendered in the UI.
  • Q&A answer display: → [answer_label] only.
  • Domain pills: None / Disrupted / Partial / Stable / Strong. Never integers.
  • Triage tier is computed output — no tier picker at any role level.

New Client Intake
— Quick Entry · 4-step form
Live Prototype — Step 2: Disaster & Housing
Role

Fast-path client creation for field use. Creates a new client record, queues a follow-up, assigns Triage Pending badge, and runs a real-time duplicate check on name + phone + address on save.

4 Steps

Layout
  • Mobile — gradient header with 4-segment step bar, step label, step title. Form card on warm-bg. Gradient CTA on white.
  • Desktop — gradient left panel (step tracker) + form on right. "Save draft" persistent.
UX Decisions
  • Progressive disclosure — one decision per step. Reduces cognitive load in field conditions.

Screen 10
Resources
— Resource hub · Bottom nav tab
Live Prototype
Role

Searchable directory of community resources organized by recovery domain. Used when a CM needs to refer a client to a housing service, food bank, mental health provider, or other support — directly from the field.

Layout
  • Search bar — real-time filtering across all resources and categories.
  • Category filter pills — All / Housing / Financial / Mental Health / Employment / Legal.
  • Resource cards — category label · name · description · [+ Add to client] gradient CTA · [Details →].
  • Highlight state — 2px teal border when accessed via ?highlight=id deep-link from Dashboard New Resources module.
UX Decisions
  • "+ Add to client" opens modal to select a client → creates AidApplication record directly.
  • Category tabs match the 5 recovery domains from Assessment — consistent mental model.
  • Search runs across all categories simultaneously — CMs often don't know which category a resource lives in.

Screen 10a
Resource Detail + Client Matching
— Resource → Client view · CM + Supervisor · Dual-pane desktop
Live Prototype — Desktop Dual-Pane
Role

Resource-first workflow. When a CM or Supervisor drills into a Resource card, they see the full resource detail and every client in their caseload who matches that resource — with matching reasons surfaced inline. Starting an application is one tap: the form pre-populates automatically.

Dual-Pane Layout
  • Left pane (58%) — resource header, ✓ Template configured chip, application form with autofill fields. Gradient "Start Application" CTA.
  • Right pane (42%) — "Matching Clients" count + filter pills. Client rows: avatar · name · 36px ring · action button.
  • Selection model — clicking a client in the right pane populates the left form. Selected row gets teal-tinted bg + green border.
Mobile

2-tab layout: "Resource Detail" tab and "Matching Clients [N]" tab. Tapping a client in Tab 2 switches to Tab 1 with that client loaded.

Matching Logic
  • Area Needs tag intersection — client's needs vs. resource's service tags.
  • Assessment domain score — clients below "Stable" in relevant domain surfaced first.
  • Recovery Score ≤ 749 — default filter. Supervisor can adjust.
  • "Already Applied" guard — shows prior submission date. Informational, not a gate.
Action Button States
[Start Application]
[Filling Form →]
[Applied {date}]
Supervisor Batch Flow

Filter to Score <500, select multiple client checkboxes → "Start Auto-Drafts for selected (N)" CTA launches pre-populated applications for all selected clients without visiting each profile individually.

Screen 05
Supervisor Dashboard — Org Overview
— Org-level command center · Supervisor / Admin
Live Prototype — Desktop
Role

The supervisor's primary screen. Full team visibility in one view — caseload, capacity status, urgency flags, and time-period metrics.

Layout
  • KPI strip (5 cards, single row) — Active Clients · CMs Active · T1+T2 Cases · Funding Approved · Open Escalations. Never stacked.
  • 3-column module row (equal) — Score Drop Alerts · CMs Over Capacity (≥35) · New Resources.
  • Intake Pipeline (full-width) — Pending → Verified → Assigned → Follow-up.
  • Period filter + Export button — always accessible in topbar.
UX Decisions
  • KPI row leads — supervisor reads org health numbers first.
  • CMs Over Capacity flag (≥35 active clients) surfaces overload proactively.
  • Score drop alerts across all CMs — deteriorating cases visible at org level.
  • Export button always accessible for grant reports and funder check-ins.

Screen 12
Metrics
— Activity analytics · CM + Supervisor · formerly "Reports"
Live Prototype
Role

Activity metrics scoped to the viewer's context — CM sees their own caseload; Supervisor sees org-wide or per-CM with ?cmId= scope. Renamed from "Reports" to "Metrics" everywhere — route stays /reports.

Layout
  • 6-card KPI strip — Notes Logged · Follow-ups Done · New Assessments · Aid Apps Submitted · Resources Approved · Funding Approved ($N).
  • Recovery Score trend — area chart, filled gradient. Green stroke = up / red stroke = down.
  • Top Movers — Improving — up to 3 clients, positive delta, compact 36px ring + ↑ N pts.
  • Top Movers — Needs Attention — negative delta, coral text.
Scope Params
  • ?cmId=<id> — scopes to that CM's caseload.
  • ?clientId=<id> — scopes to that client.
  • ← Back button appears when either param is present.
Screen 13
Intake Submissions
— 4-tab pipeline · Supervisor · Review & assign incoming clients
Live Prototype — Desktop
Role

Supervisor-managed pipeline for public intake submissions. Four stages before a client reaches a CM's active caseload.

4-Tab Pipeline
  • Pending ● — Supervisor: [Verify ✓] [Flag] [Reject]
  • Verified — CM Lead: [Assign to CM →] [Flag] [Reject]
  • Assigned — CM: [Quick Entry → Create Client]
  • Follow-up — Supervisor: [Resolve & Verify ✓] [Reject]
Candidate Card
  • Submission date · household size · language · damage type · Area Needs chips.
  • Contact lines · referral source · photo-ID warning if missing.
  • Flags: no_id · ambiguous_match · out_of_zone.
Assign Modal

Lists active CMs sorted by current caseload (least loaded first). Shows overdue count + ⚠ over-capacity flag (≥35 active clients) per CM.

Screen 14
Profile / Settings
— Profile, notifications, team · Shared · Mobile
Live Prototype
Role

App settings — profile, notifications, team management, and security. Accessible to both CMs and supervisors. Phone-primary. Low-frequency screen.

Mobile Sections (top → bottom)
  • Profile card — gradient avatar · name · role badges.
  • Organization card — org name + region.
  • Intake Link — Supervisor / Admin only.
  • Achievements — SVG icon tiles. Earned = gradient bg + white icon. Locked = gray bg + 45% opacity. No emoji anywhere.
  • Security — Face ID toggle (HIPAA — biometric only, no passcode fallback).
  • Sign Out — red text, confirmation required.
Achievement Tile Rule
  • Earned: gradient bg + white stroke SVG icon.
  • Locked: gray-100 bg + gray SVG icon + wrapper 0.45 opacity.
  • No emoji anywhere in the app.

Screen S1
Survivor Portal — Home
— Case status · Ring · CM info · Action items
Live Prototype
Role

The survivor's home screen. Shows their case status, Recovery Score ring, assigned Care Manager, and any action items (document uploads needed, signatures required). Accessed via a secure tokenized link sent by their CM — no login credentials required.

Layout
  • Gradient hero — client name, case ID, tier badge. 72px gradient ring showing their own Recovery Score. CM assignment card with "Message CM" gradient CTA.
  • Action items card — urgency-coded items with gradient CTAs (Upload / Sign).
  • Latest from CM card — most recent message preview.
  • Quick status 2×2 grid — Recovery Plan / Applications / Documents / Messages.
  • 4-tab mobile nav — My Case · Plan · Apps · Messages. No + button.
What Survivors Can NEVER Do
  • Edit any case information or assessment answers.
  • Change triage tier or Recovery Score.
  • Access other clients or CM-internal notes.
  • Start a new application without CM initiation.

Screen S2
Survivor Case File
— Recovery Plan · Applications + signature · Messages · Documents
Live Prototype — Desktop: Applications + Messages
Role

The survivor's full case view across four tabs. Applications tab is the primary state — this is where survivors sign applications their CM has prepared and see the status of all their active applications.

Applications Tab
  • Application list — read-only status rows (Approved ✓ / In Progress / Auto-Draft).
  • Signature required — card with autofill fields (green border, "Filled" chip, read-only), signature pad (tappable), and "Sign & Authorize Submission" gradient CTA.
  • Autofill fields: same green border + #F0FAF5 bg treatment as CM view, but read-only.
Signature Rule

Survivor signature collected in-app for applications requiring authorization. "Sign & Authorize Submission" gradient CTA (teal→coral→navy on white) confirms and sends to CM for final submission.

Messages Tab
  • Thread between survivor and their assigned CM only.
  • CM bubbles: white card, left-aligned, CM initials avatar.
  • Survivor bubbles: navy bg, white text, right-aligned.
  • Send button: 34px gradient circle, paper-plane SVG icon.
  • Desktop: message thread visible alongside applications in split layout.
Recovery Plan Tab

Read-only view of the AI-generated Recovery Plan. Domains shown with status labels (None / Disrupted / Partial / Stable / Strong). Survivor cannot edit goals or domain assessments.

Documents Tab

Upload interface for documents requested by the CM. Uploaded files flow directly into their case file in Vijilant.
