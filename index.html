Screen 01
Onboarding
— First-run setup · Runs once
Live Prototype
Role

First-run experience shown once on initial app launch. Configures the CM's identity, organization, and role before they reach the app's main navigation. Not reachable from within the app after completion.

Layout

Full-screen card sequence. Each step occupies the full viewport — no competing elements. Progress indicator at top communicates where the CM is in the setup sequence.

UX Decisions
  • Progressive disclosure — CM sees only what's needed per step, not the full form at once.
  • Each step is a single decision: name, org, role. Reduces cognitive load at first launch.
  • Optional sample data step — lets a CM explore the app before entering real cases.
  • Tap-to-advance interaction; required fields must be filled before the CTA enables.
Exits To
Dashboard
Screen 02
Dashboard
— Daily anchor · Home screen
Live Prototype
Role

Opens on every app launch. The morning brief — designed to answer "what needs my attention today?" without requiring the CM to go hunting. Not a list of all cases; a prioritized summary of what matters now.

Layout
  • Greeting header — personalized, date-stamped. Warm, not clinical.
  • Stat strip — 4 at-a-glance counts: Active Cases, Urgent, Follow-Ups Due, Closed (30d).
  • Today's Priority — top 3 urgent items. Sorted by severity. Tapping opens the Case File.
  • Follow-Up Queue — time-ordered upcoming actions. Day labels (THU / FRI / MON).
  • Bottom nav — persistent. Home / Clients / Resources / + (Intake).
UX Decisions
  • Morning-brief model — CMs see a curated digest, not an overwhelming list. Priority is decided by the system, not the CM.
  • Urgency color hierarchy: Red = urgent action needed · Amber = FEMA / deadline · no color = standard.
  • Stat strip is read-only — numbers orient the CM quickly but do not require tapping.
  • Follow-up queue is time-indexed, not alphabetical — next action in time order.

Screen 03
Client List
— Full caseload browser
Live Prototype
Role

Full caseload in one scrollable list. Used when the CM needs a specific case that isn't surfaced on the Dashboard, or when doing a status review across all active clients.

Layout
  • Page title — "Clients" with total count.
  • Search bar — inline, immediately below the title. Filters the list in real time.
  • Filter tabs — All / Active / Stabilizing / Closed. Scrollable if needed.
  • Case card row — Name, status badge, assigned CM initials, last-touch date.
  • FAB (+ button) — fixed bottom-right. Launches New Intake directly.
UX Decisions
  • Status badge appears before the name in the visual scan order — status is the first signal, not the last.
  • Last-touch date ("Today" / "2d ago") surfaces recency without requiring the CM to open the case.
  • Default sort: Last Updated. Most recently touched cases appear first — matches how CMs actually navigate their work.
  • Closed cases are visible but visually de-emphasized — they remain searchable and auditable.

Screen 04
Case File
— Central hub for a single client
Live Prototype
Role

Everything about one client in one place. The hub that all case-specific work flows through. Notes, assessments, plans, and aid applications are all tabs within this screen — not separate screens reached from a menu.

Layout
  • Back nav — returns CM to wherever they came from (Dashboard or Client List).
  • Client header — name, case ID, open date, assigned CM, current status badge.
  • Sticky tab bar — horizontally scrollable. Tabs: Overview · Notes · Assessment · Plan · Aid · Docs.
  • Tab content area — scrollable below the sticky tab bar. Content swaps per tab without full-screen navigation.
UX Decisions
  • Tab model keeps case complexity organized. A CM working in Notes never loses the context of whose case they're in.
  • Most-used tabs (Overview, Notes) are placed leftmost — reached without horizontal scrolling.
  • Sticky tab bar persists while scrolling tab content — CM always knows which tab is active and can switch without scrolling back to the top.
  • Active tab uses green underline and green text (#1F4D37) to match the brand primary. Inactive tabs are muted.
  • Horizontal scroll on tabs handles future tab additions without redesigning the layout.

Screen 05
Case Notes
— Notes tab within Case File
Live Prototype
Role

Chronological log of every note on a case. Where the CM records what happened, what was communicated, what was referred, and what requires follow-up. The primary documentation tool.

Layout
  • Timeline list — notes sorted newest-first. Each card shows: note type badge, timestamp, author, and content preview.
  • Compose FAB — fixed bottom-right. Opens the note composition view. Stays visible while scrolling through history.
  • Note type badge — appears before content. Type is visible before the CM reads a word.
  • Supervisor Notes tab — a secondary sub-tab within Notes, visible to supervisors. CMs see supervisor notes but cannot edit them.
Note Types

UX Decisions
  • Note type classification makes the history scannable — a supervisor or new CM can understand the arc of a case from badges alone before reading content.
  • Newest-first sort matches how CMs think about a case: what happened most recently matters most.
  • FAB position (bottom-right) follows the dominant-hand thumb zone on mobile — compose action requires zero repositioning.
  • Author + timestamp on each note creates accountability and traceability without extra UI.
Context

Lives inside Case File. Tab bar remains sticky above — CM can switch to Assessment or Plan without losing their scroll position awareness.

Screen 06
Assessment
— 12-section clinical form · Case File tab
Live Prototype
Role

Full Assessment is where CMs document the complete clinical picture — across 12 structured sections from disaster impact through client priorities. CMs fill discrete fields (radio buttons, checkboxes, dropdowns, free-text) that capture the survivor's actual situation. When the assessment is saved, the Auto-Triage Engine reads every section and assigns an official Tier designation automatically. CMs never touch the tier directly.

Layout
  • Progress bar — "X of 12 sections complete" keeps the CM oriented in a long form. Always visible; always accurate.
  • Section nav grid — 12 tiles showing state: complete (green check), in progress (active border), not started (muted). Tappable — CM can jump to any section or work sequentially.
  • Expanded section — one section open at a time, displaying its actual fields. §3 Disaster Impact is shown open here: segmented radio for damage level, checkboxes for utilities, radio list for displacement status, free-text for survivor's own words.
  • Triage tier placeholder — sits at the bottom in a pending state until the full assessment is saved. Communicates the engine's role without exposing a manual picker.

UX Decisions
  • Tier is a computed output, never a CM input — the interface has no tier picker. The CM fills the form; the Auto-Triage Engine assigns the tier on save.
  • Section nav grid keeps CMs oriented across a long form — they always know what's done and what remains without scrolling through everything.
  • §11 CM Assessment has two distinct parts: Part A (CM fills Level of Need and Recommended Tier as a clinical suggestion), Part B (Auto-Triage Engine writes the Official Tier and Rationale). Displayed as separate, labeled fields — the distinction is auditable and defensible.
  • "Save & Continue" advances section by section — preserving work-in-progress without requiring the CM to complete all 12 sections in one session.
Screen 07
Recovery Plan
— Goal tracking · Plan tab
Live Prototype
Role

Structured, actionable goal list tied to a client's recovery. Translates the Assessment's domain scores into concrete next steps. CM and client-facing — meant to be revisited on every check-in.

Layout
  • Goal rows — each goal has a checkbox, title, associated domain, due date, and status.
  • Add Goal FAB — bottom-right, visible while scrolling.
  • Completion state — checked goals shift to muted text with strikethrough. They stay in the list — they do not disappear.
  • Domain grouping — goals grouped under their recovery domain (Housing / Financial / etc.).
UX Decisions
  • Completed goals remain visible — the plan is an audit trail, not just a to-do list. CMs and supervisors can see what was accomplished.
  • Strikethrough in muted color (#9E9993) signals done without the visual clutter of a deletion.
  • Due dates on individual goals create accountability without requiring a separate calendar view.
  • Long-press interaction: edit or delete a goal. Tap: toggle completion. Two distinct actions, two distinct gestures.
Screen 08
Aid Applications
— Application tracking · Aid tab
Live Prototype
Role

Tracks every aid application filed on behalf of a client — FEMA, SBA, CalFresh, and others. Status and timeline for each application in one place, without requiring the CM to check external portals for each one.

Layout
  • Application cards — one per application type. Icon, program name, current status badge, last updated.
  • Timeline per application — event log below the card showing what happened and when (submitted, under review, approved, etc.).
  • Status badge — most prominent element on each card. Color-coded and immediately readable.

UX Decisions
  • Status is the first visual element per card — the CM does not need to read the full card to know where an application stands.
  • Timeline dots show what happened without requiring a prose narrative — the CM can scan an entire application history in seconds.
  • Appeal status uses amber (not red) — a pending appeal is active work, not a terminal state. The distinction matters for prioritization.
  • Application icons create visual separation between programs — useful when multiple FEMA/SBA/CalFresh applications exist simultaneously.
Screen 09
Resources
— Resource hub · Bottom nav
Live Prototype
Role

Searchable directory of community resources organized by recovery domain. Used when a CM needs to refer a client to a housing service, food bank, mental health provider, or other support — directly from the field.

Layout
  • Search bar — at top, real-time filtering across all resources.
  • Category tabs — Housing · Financial · Food · Mental Health · Legal · Other. Scrollable.
  • Resource cards — organization name, brief description, and inline Call / Email action buttons.
  • Persistent bottom nav — CM can return to Dashboard or Client List without losing context.
UX Decisions
  • Call and Email actions are inline on the card — no copy-paste, no navigating to a contact screen. One tap from the field.
  • Category tabs match the 5 recovery domains from Assessment — the CM's mental model is consistent across the whole app.
  • Search runs across all categories simultaneously — CMs often don't know which category a resource lives in.

Screen 10
New Intake
— New client form · FAB or bottom nav
Live Prototype
Role

Structured onboarding form for a new client. Captures everything needed to open a case — personal information, disaster event details, current housing situation, and initial case notes — in a single guided flow.

Layout
  • Progress indicator — top of screen. Shows current step of N total steps.
  • Section-per-screen model — one group of related fields per step, not a single long form.
  • Sections — Personal Info · Disaster Event · Housing Status · Household Members · Initial Notes.
  • Required field markers — inline, visible before submission. Not revealed on error.
  • Back / Next CTAs — bottom of each step. Back is always available.
UX Decisions
  • Grouped sections reduce cognitive load — CM sees 4–6 fields per step, not 25 at once.
  • Progress bar gives the CM a sense of completion — "3 of 5" prevents abandonment mid-form.
  • Required fields are marked from step one — no error-first discovery.
  • Initial notes field captures verbal information in the field before the CM has time to return to a desk.

Screen 11
CM Board
— Desktop command center
Live Prototype
Role

Desktop-optimized command center for desk-based case work. Same data as mobile, reorganized for a 1280px viewport — higher information density, persistent navigation, global search always visible.

Layout
  • Left sidebar (220px) — persistent nav. Brand Green (#1F4D38) background — signals CM identity at a glance. Logo mark at 15% white opacity. Nav text at 65% white (inactive), full white with 18% overlay pill (active). No border — sidebar meets the content area clean.
  • Top bar — screen title, global search field (220px), user avatar.
  • Main content area — adapts to selected nav item. Dashboard / Cases / Reports / Settings.
  • Window chrome — macOS-style titlebar with traffic light buttons.
UX Decisions
  • Sidebar navigation persists — the CM never loses their orientation regardless of which view is active.
  • Global search in the top bar — accessible from every screen without a dedicated search flow.
  • Desktop affords a data density mobile cannot — more cases, more columns, more information visible simultaneously without scrolling.
  • Dark green sidebar creates immediate role identity — a CM opening their desktop view sees their color immediately, not a neutral chrome. The mobile bottom nav uses the same Brand Green for active states, keeping the language consistent across platforms.
  • Nav badges (red dot with count) surface urgent items in the sidebar itself — CM sees urgency before clicking into a section.

Screen 12
Supervisor Dashboard
— Org-level command center · Desktop
Live Prototype
Role

The supervisor's primary screen. Full team visibility in one view — every CM's caseload, capacity status, urgency flags, and time-period metrics. Designed for desk use at the start of each day and during team check-ins.

Layout
  • KPI row (5 cards) — Total Active Cases · Avg Cases per CM · FEMA Actions Pending · Flagged Cases · Completed This Month. Large numbers, color-coded for urgency (green / amber / red).
  • Three-column body — CM workload table (left), flagged case queue (center), activity feed (right, 320px).
  • Topbar — Time period filter (Today / Week / Month) + Export button. Persistent on scroll.
  • Left sidebar (220px) — Green Light (#EAF3EF) background with #C8E0D5 border — signals Supervisor identity. Logo badge inverted to solid green on light field. Nav section labels in #7A9E8E. Active nav item uses a white pill (#FFFFFF bg, #1F4D38 text) so it reads clearly against the soft green field.
UX Decisions
  • KPI row leads the page — supervisor reads the numbers first, before any table or list. Prevents supervisor from needing to scan rows to understand org health.
  • CM workload table shows case count, last activity, and capacity status per row — supervisor can identify who's overloaded before a CM raises a flag.
  • Flagged case queue is second column, not buried — urgency is always visible alongside team workload, not in a separate report.
  • Export button in the topbar, always accessible — supervisor exports for grant reports and funder check-ins without navigating to a separate Reports page.
  • Time period filter applies globally to all three columns simultaneously — one toggle re-scopes the entire view.

Screen 13
CM Metrics
— Individual CM drill-down · Desktop
Live Prototype
Role

Detailed performance and workload view for a single CM — or the team in aggregate. Not a top-level nav item. Reached via drill-down from the Supervisor Dashboard. Gives supervisors outcome data, not just activity counts.

Layout
  • KPI row — Cases Opened · Cases Closed · Notes Filed · Avg Response Time. Same card pattern as supervisor dashboard for visual consistency.
  • Case timeline — chronological strip of recent case activity for this CM. Each entry links to the full case file.
  • Outcome distribution — visual breakdown of cases by recovery domain status (Housing, Financial, Health, Legal, Emotional).
  • Aid referral stats — counts of FEMA referrals, grant submissions, and resource connections made by this CM in the period.
UX Decisions
  • Drill-down only — this screen is never reached from a CM's own nav. Supervisors see it; CMs do not. Keeps metrics transparent at the org level without making CMs feel surveilled in their daily flow.
  • Outcome data, not just volume — supervisor can distinguish a CM carrying 50 actively-progressing cases from one carrying 50 stalled cases. Case count alone doesn't tell that story.
  • Same time period filter as the Dashboard — if supervisor is looking at "this week" in Screen 12, CM Metrics opens in the same period for continuity.
  • Back navigation is explicit — supervisor returns to the Dashboard row they came from, not a generic home screen.

Screen 14
Settings
— Profile, notifications, team · Shared · Mobile
Live Prototype
Role

App settings — profile, notifications, team management, and security. Accessible to both CMs and supervisors. Phone-primary; same controls surface in the desktop sidebar's bottom section. Low-frequency screen — visited for setup and the occasional change, not daily use.

Layout
  • Profile block — photo, name, role badge at top. Immediate identity confirmation. Tap to edit.
  • Settings groups — Profile · Notifications · Team · Security · About. Each group is a tappable row with chevron navigation.
  • Role-conditional sections — Team section visible to supervisors only. CMs see their own org and team, but cannot manage members.
UX Decisions
  • Settings is last in nav priority — bottom nav position reflects frequency of use. Not hidden, but not competing with active-work screens.
  • Notification settings are meaningful for field CMs — high-stress environments require control over what interrupts them. Granular controls (urgent only / all / off) per category.
  • Profile is the first row — user confirms they're logged in as the right person before changing anything. Reduces accidental edits under shared devices.
  • Role-conditional visibility prevents confusion — a CM who sees a "Team Management" section they can't use is friction. Supervisor-only features are hidden from CMs, not disabled.
