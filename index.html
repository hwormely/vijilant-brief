Screen 01
Onboarding
— First-run setup · Runs once
Live Prototype
Role

First-run experience shown once on initial app launch. Configures the CM's identity, organization, and role before they reach the app's main navigation. Not reachable from within the app after completion.

Layout

Full-screen card sequence. Each step occupies the full viewport — no competing elements. Progress indicator at top communicates where the CM is in the setup sequence.

UX Decisions
  • Progressive disclosure — CM sees only what's needed per step, not the full form at once.
  • Each step is a single decision: name, org, role. Reduces cognitive load at first launch.
  • Optional sample data step — lets a CM explore the app before entering real cases.
  • Tap-to-advance interaction; required fields must be filled before the CTA enables.

Screen 02
Dashboard
— Daily anchor · Home screen
Live Prototype
Role

Opens on every app launch. The morning brief — designed to answer "what needs my attention today?" without requiring the CM to go hunting. Not a list of all cases; a prioritized summary of what matters now.

Layout
  • Greeting header — personalized, date-stamped. Warm, not clinical.
  • Stat strip — 4 at-a-glance counts: Active Cases, Urgent, Follow-Ups Due, Closed (30d).
  • Today's Priority — top 3 urgent items. Sorted by severity. Tapping opens the Case File.
  • Follow-Up Queue — time-ordered upcoming actions. Day labels (THU / FRI / MON).
  • Bottom nav — persistent. Home / Clients / Resources / + (Intake).
UX Decisions
  • Morning-brief model — CMs see a curated digest, not an overwhelming list. Priority is decided by the system, not the CM.
  • Urgency color hierarchy: Red = urgent action needed · Amber = FEMA / deadline · no color = standard.
  • Stat strip is read-only — numbers orient the CM quickly but do not require tapping.
  • Follow-up queue is time-indexed, not alphabetical — next action in time order.

Screen 03
Client List
— Full caseload browser
Live Prototype
Role

Full caseload in one scrollable list. Used when the CM needs a specific case that isn't surfaced on the Dashboard, or when doing a status review across all active clients.

Layout
  • Page title — "Clients" with total count.
  • Search bar — inline, immediately below the title. Filters the list in real time.
  • Filter tabs — All / Active / Stabilizing / Closed. Scrollable if needed.
  • Case card row — Name, status badge, assigned CM initials, last-touch date.
  • FAB (+ button) — fixed bottom-right. Launches New Intake directly.
UX Decisions
  • Status badge appears before the name in the visual scan order — status is the first signal, not the last.
  • Last-touch date ("Today" / "2d ago") surfaces recency without requiring the CM to open the case.
  • Default sort: Last Updated. Most recently touched cases appear first — matches how CMs actually navigate their work.
  • Closed cases are visible but visually de-emphasized — they remain searchable and auditable.

Screen 04
Case File
— Central hub for a single client
Live Prototype
Role

Everything about one client in one place. The hub that all case-specific work flows through. Notes, assessments, plans, and aid applications are all tabs within this screen — not separate screens reached from a menu.

Layout
  • Back nav — returns CM to wherever they came from (Dashboard or Client List).
  • Client header — name, case ID, open date, assigned CM, current status badge.
  • Sticky tab bar — horizontally scrollable. Tabs: Overview · Notes · Assessment · Plan · Aid · Docs.
  • Tab content area — scrollable below the sticky tab bar. Content swaps per tab without full-screen navigation.
UX Decisions
  • Tab model keeps case complexity organized. A CM working in Notes never loses the context of whose case they're in.
  • Most-used tabs (Overview, Notes) are placed leftmost — reached without horizontal scrolling.
  • Sticky tab bar persists while scrolling tab content — CM always knows which tab is active and can switch without scrolling back to the top.
  • Active tab uses green underline and green text (#1F4D37) to match the brand primary. Inactive tabs are muted.
  • Horizontal scroll on tabs handles future tab additions without redesigning the layout.

Role

Chronological log of every note on a case. Where the CM records what happened, what was communicated, what was referred, and what requires follow-up. The primary documentation tool.

Layout

  • Compose FAB — fixed bottom-right. Opens the note composition view. Stays visible while scrolling through history.
  • Note type badge — appears before content. Type is visible before the CM reads a word.
  • Supervisor Notes tab — a secondary sub-tab within Notes, visible to supervisors. CMs see supervisor notes but cannot edit them.

  • Note type classification makes the history scannable — a supervisor or new CM can understand the arc of a case from badges alone before reading content.

Screen 06
Assessment
— 12-section clinical form · Case File tab
Live Prototype
Role

Full Assessment is where CMs document the complete clinical picture — across 12 structured sections from disaster impact through client priorities. CMs fill discrete fields (radio buttons, checkboxes, dropdowns, free-text) that capture the survivor's actual situation. When the assessment is saved, the Auto-Triage Engine reads every section and assigns an official Tier designation automatically. CMs never touch the tier directly.

Layout
  • Progress bar — "X of 12 sections complete" keeps the CM oriented in a long form. Always visible; always accurate.
  • Section nav grid — 12 tiles showing state: complete (green check), in progress (active border), not started (muted). Tappable — CM can jump to any section or work sequentially.
  • Expanded section — one section open at a time, displaying its actual fields. §3 Disaster Impact is shown open here: segmented radio for damage level, checkboxes for utilities, radio list for displacement status, free-text for survivor's own words.
  • Triage tier placeholder — sits at the bottom in a pending state until the full assessment is saved. Communicates the engine's role without exposing a manual picker.

UX Decisions
  • Tier is a computed output, never a CM input — the interface has no tier picker. The CM fills the form; the Auto-Triage Engine assigns the tier on save.
  • Section nav grid keeps CMs oriented across a long form — they always know what's done and what remains without scrolling through everything.
  • §11 CM Assessment has two distinct parts: Part A (CM fills Level of Need and Recommended Tier as a clinical suggestion), Part B (Auto-Triage Engine writes the Official Tier and Rationale). Displayed as separate, labeled fields — the distinction is auditable and defensible.
  • "Save & Continue" advances section by section — preserving work-in-progress without requiring the CM to complete all 12 sections in one session.
Screen 07
Recovery Plan
— Goal tracking · Plan tab
Live Prototype
Role

Structured, actionable goal list tied to a client's recovery. Translates the clinical assessment into concrete next steps — organized by recovery area. CM and client-facing — meant to be revisited on every check-in.

Layout
  • Goal rows — each goal has a checkbox, title, associated domain, due date, and status.
  • Add Goal FAB — bottom-right, visible while scrolling.
  • Completion state — checked goals shift to muted text with strikethrough. They stay in the list — they do not disappear.
  • Domain grouping — goals grouped under their recovery domain (Housing / Financial / etc.).
UX Decisions
  • Completed goals remain visible — the plan is an audit trail, not just a to-do list. CMs and supervisors can see what was accomplished.
  • Strikethrough in muted color (#9E9993) signals done without the visual clutter of a deletion.
  • Due dates on individual goals create accountability without requiring a separate calendar view.
  • Long-press interaction: edit or delete a goal. Tap: toggle completion. Two distinct actions, two distinct gestures.
Screen 08
Aid Applications
— Application tracking · Aid tab
Live Prototype
Role

Dual-purpose: application tracker and in-app application builder. A CM tracks every aid application filed for a client — and can complete and submit the application itself from within Vijilant, with client data pre-populated. Supervisors (ED, CM Lead, Resource Lead) configure the application templates. CMs fill and submit.

Configurable — and importable

Supervisors build an application template field-by-field, or import the aid partner's existing form — upload a PDF or DOCX, or paste a link, and Vijilant configures it into a ready-to-use template. No retyping a partner's 17-field application by hand.

At the enterprise tier this extends org-wide: each DCM organization configures its own intake questionnaire and recovery assessment inside Vijilant — the same engine that fits Vijilant to LLP fits it to any agency. Option entry-points are live in the app today (Template Builder import + Organization Setup); the auto-parsing and per-org configuration engines are the enterprise / v2 build.

Two Access Paths
Client Profile → Aid tab
→
Applications for this client
Resources → Select Resource
→
All matching clients + Apply

Path 1 is client-first: CM is in a case file and needs to apply to a specific program. Path 2 is resource-first: a new funding stream opens and the CM (or Supervisor) wants to see every client who qualifies and batch-initiate applications — without visiting each profile one by one.

Auto-Fill System

When a CM opens an application form for a client, Vijilant pre-populates every field it can from the client's profile. For the Wylie Center Intake Form, 15 of 17 fields auto-fill — name, DOB, contact, address, household size, marital status, language preference, employment status, insurance, damage type. The remaining 2 fields (specific documentation dates) require CM input.

Auto-filled — green left border · "Auto-filled from profile" chip · background tint (#F0FAF5)
Requires input — standard field, no fill indicator
Template Configurator

Supervisor-only. Accessible via Resource Detail → "Edit Application Template" or Settings → Aid Templates. Field builder mirrors the Assessment configurator: drag to reorder, add/remove fields, set field type (text, date, select, multi-select, file upload), and map each field to a profile_field_mapping key so Vijilant knows what client data to pull. Saves to aid_templates + aid_template_fields.

Submission Modes
  • Email submission — always available. Vijilant compiles the completed form + attachments and sends to the configured recipient address on the template. CM receives a sent confirmation; submission logged to audit trail.
  • API submission — available when the AID org provides an endpoint. Configured on the template by a Supervisor. Vijilant POSTs the answers directly; response status reflected on the application card.
  • External Form — for Jotform / Salesforce orgs (Salvation Army, Habitat LA). Vijilant opens the form URL in a browser sheet, pre-fills available URL params, and the CM completes the final submission in the external form. Vijilant records the attempt and lets the CM mark it submitted.

Auto-Draft

Auto-Draft — new status. Appears when Vijilant has pre-populated an application from the client profile but the CM has not yet reviewed or submitted. Blue distinguishes it from a CM-initiated draft — the system started it, the CM finishes it.

UX Decisions
  • Auto-filled fields use a green left border (2px, Brand Green) — the CM immediately sees what the system populated vs. what needs their input. No color-only signal: the "Auto-filled" chip is always present for screen reader access.
  • Submission mode selector appears at the bottom of the application form — CM chooses Email, API, or External Form before hitting Submit. Default is the mode configured on the template by the Supervisor.
  • Timeline dots log every action: auto-draft created, CM reviewed, submitted, response received. Full audit trail without CM writing a note.
  • Applications from both access paths (Client Profile and Resource Detail) land in the same aid_applications table and appear on the client's Aid tab — no duplication, single source of truth.
  • Appeal status uses amber (not red) — a pending appeal is active work, not a terminal state.

Start Application
Role

Resource-first workflow. When a CM or Supervisor drills into a Resource card from the directory, they see the full resource detail and every client in their caseload who matches that resource — with matching reasons surfaced inline. Starting an application for any client is one tap: the form pre-populates automatically.

Dual-Pane Layout
  • Left pane (58%) — resource header (name, category tags, availability status), auto-fill banner (% pre-populated), application form fields. Green left border + "Auto-filled" chip on every pre-populated field.
  • Right pane (42%) — "Matching Clients" list. Filter pills at top (Score threshold, Assessment domain, Needs tags). Each row: client avatar, name, match reason tags, recovery score. "Start Application" or "Already Applied" CTA per row.
  • Selection model — clicking a client in the right pane populates the left pane form with that client's data. Highlighted row in green confirms selection.
Matching Logic
  • Area Needs tags — client's recorded needs (from intake or assessment) intersect with resource's service tags (Housing, Financial, Food, etc.).
  • Recovery Score + assessment answers — clients whose assessment answers indicate need (e.g., Housing status: None or Disrupted) in the resource's relevant area are surfaced first.
  • Recovery Score band — resource eligibility thresholds (e.g., Score ≤ 499) filter automatically. Supervisor can adjust the filter pill at the top of the pane.
  • "Already Applied" guard — Vijilant checks aid_applications and shows prior submission date on the row. Prevents duplicate applications without blocking the CM from seeing the full list.
UX Decisions
  • Dual-pane is desktop-primary. On mobile, the resource detail and client list are separate tabs within the resource drawer — same data, stacked rather than side-by-side.
  • "Already Applied" status is informational, not a gate — the CM can still start a new application if needed (e.g., re-application after denial). The guard is a prompt, not a lock.
  • Supervisor scope: sees all clients in the org database. CM scope: sees own assigned caseload only. The matching query respects RLS automatically.
  • Supervisor can use this view to orchestrate a batch application campaign — filter to Score < 500, select all eligible clients, initiate auto-draft applications in sequence without opening each profile individually.

Live Prototype
Role

The supervisor's primary screen. Full team visibility in one view — every CM's caseload, capacity status, urgency flags, and time-period metrics. Designed for desk use at the start of each day and during team check-ins.

Layout
  • KPI row (5 cards) — Total Active Cases · Avg Cases per CM · FEMA Actions Pending · Flagged Cases · Completed This Month. Large numbers, color-coded for urgency (green / amber / red).

  • Flagged case queue is second column, not buried — urgency is always visible alongside team workload, not in a separate report.
  • Export button in the topbar, always accessible — supervisor exports for grant reports and funder check-ins without navigating to a separate Reports page.
  • Time period filter applies globally to all three columns simultaneously — one toggle re-scopes the entire view.

MOBILE — A
Recovery Plan
— Case Manager
MOBILE
OVERVIEW

Replaces the Goals tab — renamed to Recovery Plan to match LLP's recovery-first language. Each client has a structured recovery trajectory across five areas: Housing, Financial, Health, Legal, and Emotional. The CM owns goal creation; the assessment engine owns triage scoring.

WHAT'S ON SCREEN
  • 4-chip summary strip — Active / Completed / Overdue / Total. Instant caseload snapshot before scrolling into goals.
  • GoalCard — title, category chip, due date, progress bar (green fill), last-updated timestamp.
  • Green FAB (+) — bottom-right. Launches AddGoalModal. Always visible while scrolling.
  • Overdue goals surface an amber timestamp and a red progress fill to signal urgency without a separate list.
DOMAINS

Housing · Financial Assistance · Health · Documentation · Support Network

KEY DECISIONS
  • Triage tier is computed by the assessment engine — never a manual input field or dropdown.
  • Recovery Plan goals are CM-authored. Triage informs urgency; CMs author the actual plan.
  • Progress percentage is CM-updated, not auto-computed — preserves casework judgment over mechanical tracking.
MOBILE — B
Resource Matching
— Case Manager · Client Detail
MOBILE
OVERVIEW

AI-generated resource recommendations attached to each client. Score 0–100 based on client profile and assessment data. Sorted descending by match_score. Lives inside the Client Detail as a tab — not a separate screen.

STATUS FLOW

Suggested → Accepted → Referred

CM taps a resource card to accept or dismiss. Referred = CM has actively connected the client. All state changes are audit-logged.

KEY FIELDS
  • match_score — 0–100, displayed as a colored pill (green ≥75, gray below)
  • match_reason — AI-generated plain-language explanation shown in card body
  • trigger_type — what event generated the match (assessment, intake, manual)
  • cm_feedback — CM's accept/dismiss/note after reviewing
EMPTY STATE

"No resource matches yet — complete an assessment to generate matches." Empty state is informative, not just a blank list.

MOBILE — C
Duplicate Detection
— Case Manager · Add Client
MOBILE
OVERVIEW

Prevents duplicate client records before they're created. The DuplicateWarningModal fires on the Add Client form when name, phone, or email matches an existing record. It is a guardrail — not a blocker. CMs can always proceed intentionally.

HOW IT WORKS

Three parallel Supabase queries on blur of first/last name, phone, or email fields — name ILIKE match, phone partial match, email ILIKE match. Results are deduplicated by ID and capped at 5 candidates. If any match is found, the modal fires before the form submits.

ACTIONS
  • Go Back (outline) — dismisses modal, returns to form so CM can review/edit fields
  • Save Anyway (amber fill) — confirms the CM intends to create a new record despite the match. Proceeds with form submission.
TRIGGER

Fires on blur of first/last name, phone, or email fields — not on every keystroke. Debounced to avoid excessive queries.

MOBILE — D
Escalations
— Case Manager + Supervisor
MOBILE
OVERVIEW

CMs can flag any client for supervisor attention via the Actions menu (⋮) — not a tab, not a prominent button. Intentionally de-emphasized to prevent over-escalation. The friction is by design.

CM FLOW

MOBILE — E
Badges
— Case Manager · Me Tab
MOBILE
OVERVIEW

Achievements awarded automatically via Postgres RPC (award_earned_badges). Triggered by casework milestones — not gamification for its own sake. Surfaced on the Me tab as a secondary section below the CM's profile.

CATEGORIES + COLORS
  • Notes — green
  • Assessments — blue
  • Goals — amber
  • Follow-Ups — purple
  • Documents — red
  • Caseload — teal
IMPLEMENTATION
  • Best-effort fire-and-forget — badge errors are swallowed so they never block CM workflow.
  • award_earned_badges RPC runs after qualifying actions (note saved, assessment submitted, goal created, etc.).
  • Unlocked badges render full color; locked badges render gray with reduced opacity.
  • staleTime: 5 minutes — badge count doesn't need real-time accuracy.
MOBILE — F
Intake Queue
— Supervisor / Admin only
MOBILE
OVERVIEW

Supervisor and Admin only. Accessible via Me tab → Review Intake Queue button. CMs cannot see this screen — it is hidden behind a role check at the component level, not just the route level.

ACCESS GATE

Available to Supervisors and Admins only. Care Managers see their own dashboard view.

FILTER TABS

Pending · Accepted · Rejected — filters the submission list in-place. Pending is the default view; it contains the active work queue. Accepted and Rejected are the historical record.

ACTIONS
  • Accept (green fill) — creates a new client record from the intake submission data. Requires confirmation.
  • Reject (red outline) — marks submission as rejected with optional rejection reason. Requires confirmation.
  • Both actions fire only after a confirmation dialog — no accidental accepts or rejects.
